# 计算机网络的应用层如何工作

## 学习应用层前，需要先知道的网络基础

计算机网络的本质，是让不同设备上的程序能够交换数据。例如，浏览器访问网页，本质上就是浏览器向远端服务器发送请求，服务器处理后再返回响应。

网络通信通常采用**分层设计**：比较经典的一个分层模型是——应用层、传输层、网络层和链路层。**本文要介绍的就是应用层**

这里简单概述一下各层如何工作以及数据如何通过网络传输的：**应用层**就是我们的应用程序工作的位置，是整个分层模型的顶层，它依靠我们广大应用开发者写的代码将数据封装成 HTTP、HTTPS等应用层协议报文，传到下一层；第二层是**传输层**，它的意义是给应用层报文多包装一层控制信息，规定进程级别的数据如何传输，和操作系统密切配合，进一步将应用层报文包装成 TCP、UDP 等传输层协议报文，再传递到下一层；第三层是**网络层**，它的工作是帮助数据在用户主机之间的广大网络中传播、路由，我们熟知的 IP 协议就工作在这层，在这层系统会把传输层报文包装成 IP 报文等网络层协议报文，再传递到下一层；最后一层是链路层，它聚焦于系统中软硬件结合的底层，依靠 ARP 等协议判断怎么把数据发到目标机器，还涉及到数据怎么以光电信号在实际的物理网络中传播

也就是说，你想要用你的主机应用发送消息到你朋友的主机应用上，数据要在你的主机上经过应用层-传输层-网络层-链路层的层层包装，然后发到四通八达的网络中，依靠网络层正确路由和链路层作为媒介（应用层和网络层在此期间不参与），到达你朋友的主机，再层层解封以原样的数据到达应用程序后再经过程序员的代码逻辑进行处理，最后展示在你朋友面前

这样，你就对网络的工作流程有了基础了解，本系列也会参照分层模型和网络编程知识去介绍计算机网络知识，首先从应用层开始讲

**！！！注意**，本文乃至本系列从不力求面面俱到的教科书式讲解，而是以重点样例为引深入理解核心知识，比如讲报文就主要以HTTP 和 HTTPS 为例，讲应用层通信架构就主要以 浏览器-服务器 架构为例……

## 应用层是做什么的

网络层负责把数据送到目标主机，传输层负责把数据送到目标进程，但它们并不知道这些数据代表什么

例如，一串字节：

```
47 45 54 20 2f 20 48 54 54 50 ...
```

传输层只负责传输这些字节；应用层协议才规定这些字节应被解释为什么样子

因此，应用层的核心作用是：**规定不同主机上的应用程序如何组织、解释和交换消息。**

应用层关注的是**消息的业务含义**，而不是数据具体经过哪些路由器

## 应用层协议通识

### 概念

应用层协议是通信双方共同遵守的一套规则，通常规定应用层报文类型、报文格式、字段语义……

以 HTTP 协议为例，一个 HTTP 请求报文长下面这个样：

它由四部分组成：**请求行、请求头、空行、请求体**

每一部分怎么排列、怎么组织都按协议说了算，而内容是由应用程序来自定义的

```cpp
//请求行：
GET /users/123?detail=true HTTP/1.1 //使用协议版本是 HTTP1.1，请求方法是 GET，请求资源路径是 /users/123?detail=true
//请求头：一些约束字段
Host: api.example.com 
User-Agent: Mozilla/5.0
Accept: application/json
Connection: keep-alive
//空行
（空行）
//请求体：真正的交互数据
请求体数据
```

## 应用层协议如何依靠传输层

前面说过，应用层协议本身并不会真正负责把数据送到网络中的另一台机器

```http
GET /users/123 HTTP/1.1
Host: api.example.com
```

这只是规定了对方收到 HTTP 报文后按 HTTP 格式解析这一串字节会得到什么样的结果 

但 HTTP 本身并不会直接指定操作网卡、选择网络路由、处理 IP 数据包、判断数据有没有丢失……这些都**交给传输层或更下层去处理**

可以先把两层之间的关系理解为：

```text
应用层：
“我要发送什么内容，双方应该如何理解这些内容”
        ↓
传输层：
“这些字节应该以什么方式交给对面的应用进程”
```

例如 *HTTP/1.1 和 HTTP/2 通常依靠 TCP：HTTP -> TCP -> IP -> 链路层*

而*传统 DNS 查询通常依靠 UDP：DNS -> UDP -> IP -> 链路层*

这里面， TCP 和 UDP 就是工作在传输层的

应用层报文传输依赖传输层，传输层又有着不同协议，这意味着**在设计应用层协议时为了达到更好的传输效果，不能完全无视传输层**

它必须知道：**自己下面的传输协议究竟能够提供什么能力，又有哪些事情需要应用层自己负责**

### TCP 给应用层提供了什么

TCP 主要向应用层提供：

```cpp
面向连接//先建立双方的稳定连接，再互发应用层消息
可靠传输//尽量保证每次发送的 TCP 报文对方都能收到
按序交付//每个报文按序号发出、收到后按序号组装
字节流//多次发送的报文可能被一次接收，再无明确报文语义，形成无边界的字节流
流量控制//接收方根据自己的接收窗口大小告诉发送方最多发多少字节
拥塞控制//发送方根据网络状况判断最多发多少字节
```

**TCP 是字节流协议。**什么意思？

```cpp
//假设应用程序连续调用：
send(socket, "hello", 5);
send(socket, "world", 5);
//你可能会自然认为，对方也会对应收到：
hello
world
//但 TCP 并没有承诺这一点，对于 TCP 来说，它看到的只是连续的一串字节。接收端可能一次读取：
helloworld
//也可能
第一次：hel
第二次：loworld
```

因为 TCP 真正保证的是：**最终交给接收方应用程序的字节内容是正确、有序的**，而不是一次 `send()` 必须对应对方的一次 `recv()`

这也是所谓 TCP**“粘包、拆包”**问题产生的根源

因此，**建立在 TCP 上面的应用层协议必须自己解决：一个应用层消息究竟从哪里开始，到哪里结束**

例如 HTTP/1.1 中的：

```http
Content-Length: 100
本质上就在告诉接收方：接下来 HTTP Body 有 100 个字节
```

```http
Transfer-Encoding: chunked  
则通过分块格式定义消息边界
```

```text
很多应用层协议报文中都有：
Length
Body Length
Content-Length
Payload Length
```

这些大多数都是为了解决 TCP 的粘包和拆包

### TCP 的可靠性意味着什么

TCP 还为应用提供可靠传输

例如底层某个 TCP 数据段在网络中丢失：发送 A B C，实际到达 A  C。TCP 会发现 B 没有被正确确认，并尝试重新发送

最终向应用层交付 A B C

应用层通常不需要自己实现：每个 TCP 包的确认 / 重传 / 数据排序 / 重复数据消除

但是这里有一个非常重要的边界：**TCP 的可靠，不等于业务一定可靠**

举个例子，用户转账 100 元，客户端因此向服务端发送“转账 100 元”，服务端收到请求并完成转账，根据 TCP 要求，需要回复一个确认报文，但确认报文丢失，未到达客户端。客户端认为需要重传，于是再次发送“转账 100 元”报文，但从业务层面理解，无法确认这到底是不是用户真的想要再次转账，而 TCP 并不会考虑这些。**因此业务语义的可靠性，一定要靠应用层保证**

所以真实业务经常会设计：request_id、订单号、幂等 Token……帮助服务端判断重复请求

### UDP 给应用层提供了什么

UDP 与 TCP 不同，它是**面向数据报**的，数据报就是以报文为单位，而不是像 TCP 一样松散的字节流

```cpp
//例如：
sendto(socket, "hello", 5, ...);
sendto(socket, "world", 5, ...);
//UDP 会把它们看作两个独立的数据报：
UDP 数据报 1：hello
UDP 数据报 2：world
```

也就是说：**UDP 会保留应用层每次发送的数据报边界**，但是 UDP 提供的能力远少于 TCP。

它不保证：数据一定到达、数据按顺序到达、数据只到达一次、丢包以后自动重传

因此，如果应用层需要这些能力，就必须自己实现

例如传统 DNS 查询通常使用 UDP。DNS 的超时和重试逻辑是由 DNS 客户端自己实现的，而不是 UDP

### 为什么应用层要根据需求选择 TCP 或 UDP

不同应用的需求不同

一些应用不能接受一段数据莫名其妙丢失，所以需要可靠传输，如 HTTP/1.1、MySQL、很多 RPC 协议……**大量运行在 TCP 之上**

实时语音、视频、游戏更强调实时性，某个报文如果丢失后再重传回来已经失去意义，或者丢失一个报文是可以接受的，所以**它们宁愿少量丢失，也不愿为了保证绝对按序而等待太久，所以采用 UDP**

比如视频通话，某一帧画面报文丢失了，3秒后再重传回来，没有任何意义

## HTTP

HTTP 全称：HyperText Transfer Protocol，超文本传输协议。虽然名字叫“超文本传输协议”，但现代 HTTP 早已不仅仅用于传输 HTML

我们日常开发中的：HTML、JSON、CSS、图片、文件……大量数据都可以通过 HTTP 传输

HTTP 最核心的通信模型非常简单：

```text
客户端
  │
  │ Request
  ↓
服务器

服务器
  │
  │ Response
  ↓
客户端
```

真正复杂的地方在于：

- 请求怎么描述？

- 数据边界怎么判断？

- 多个请求能不能复用连接？

- 服务器怎么识别用户？

- 数据能不能缓存？

- 通信内容怎么加密？

- 一个连接如何并发多个请求？

HTTP 几十年的发展，本质上就是围绕这些问题不断演进

### HTTP/1.1 报文

HTTP/1.1 请求报文通常由：**请求行、请求头、空行、请求体**构成，例如：

```http
POST /users HTTP/1.1                          
Host: api.example.com
Content-Type: application/json
Content-Length: 27

{"name":"Tom","age":20}
```

响应报文则通常由：状态行、响应头、空行、响应体组成，例如：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 25

{"id":123,"name":"Tom"}
```

### HTTP 方法

HTTP 中常见的方法包括：GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS

常见的几个方法的语义是：

```text
GET = 查询
POST = 新增
PUT = 修改
DELETE = 删除
```

不过 HTTP 并没有强制规定，比如要求 POST 请求一定只能创建数据，这些更多属于 API 设计层面的约定

### 幂等性

应用开发中必须理解一个概念：**幂等**

简单来说：同一个操作执行一次，与重复执行多次，最终业务状态相同。

例如：

```http
DELETE /users/100
```

第一次删除用户 100，第二次用户已经不存在，执行十次以后，最终状态仍然是用户 100 不存在

所以 DELETE 在语义上通常被认为是幂等方法

而：

```http
POST /orders
```

如果每执行一次都创建一个新订单，那么这个操作通常不是幂等的。

为什么网络开发尤其在乎幂等？

还是因为网络具有不确定性：服务端没有回复响应，客户端不知道到底是服务端没处理，还是服务端已经处理但响应丢失，于是就会产生重试问题

因此：**幂等设计是应用层处理网络不确定性的重要手段**

### HTTP 状态码

HTTP 响应需要告诉客户端：请求处理结果怎么样。这个结果用状态码表示，它是一个数值

状态码通常可以按照第一位理解：

- 1xx：处理中
- 2xx：成功
- 3xx：重定向或缓存相关
- 4xx：客户端请求侧的问题
- 5xx：服务端处理侧的问题

### HTTP 的连接

HTTP 属于应用层协议。HTTP/1.1 通常运行在 TCP 上

所以 HTTP 请求真正发送前，需要先拥有一条 TCP 连接

但如果每个 HTTP 请求都重新建立 TCP 连接，成本会非常高。因为 TCP 是有三次握手、四次挥手机制的，这点在 *传输层* 篇细讲

因此 **HTTP/1.1 默认支持持久连接**。可以用一条 TCP 连接发送多次 HTTP 的请求和响应

这就是 HTTP Keep-Alive 的核心思想：**尽量复用已经建立好的 TCP 连接**

需要注意HTTP Keep-Alive 和 TCP Keepalive 不是一回事，TCP Keepalive 是操作系统通过探测报文检查长期空闲的 TCP 连接是否活着

## Cookie、Session 与认证

HTTP 有一个非常重要的特性：**HTTP 本身是无状态协议**

什么是无状态？比如服务器收到两个 HTTP 请求，但从 HTTP 协议本身来看，服务器并不知道这两个请求是不是同一个用户发送的，因为协议没有规定报文应该保存用户状态

于是有了这样的场景，例如用户登录：

```http
POST /login
```

服务器验证账号密码成功

过一会儿用户请求：

```http
GET /orders
```

服务器就必须知道：这是哪位已登录用户发的

于是产生了：**Cookie、Session、Toke、JWT**等状态管理和认证机制。

### Cookie

Cookie 本质上是：浏览器保存并在满足条件时自动携带的一小段数据

发送 HTTP 请求时服务器响应：

```http
Set-Cookie: session_id=abc123
```

浏览器保存：session_id=abc123

之后再次访问对应站点时，浏览器自动给 HTTP 请求报文添上：

```http
Cookie: session_id=abc123
```

为了让服务器知道这是哪个会话、哪个用户发的请求

需要注意，Cookie 本身并不等于登录状态。Cookie 只是浏览器的一种数据保存和自动携带机制

你完全可以使用 Cookie 保存各种其他信息，如语言偏好、主题设置……

### Session

Session 通常表示**服务端保存的一份会话状态**

例如用户登录：

```text
用户提交账号密码
     ↓
服务器验证
     ↓
生成随机 Session ID
     ↓
服务器在内存重保存映射：abc123 → userId=10086
```

浏览器后面每次请求带上 Session ID 返回给浏览器。

服务器拿到 abc123 查询 Session，从而知道当前用户身份和其他用户信息

- Cookie=客户端保存机制
- Session=服务器状态保存机制

二者经常搭配使用，但并不是同一个东西

### 分布式环境下的 Session

单机情况下，Session 放在服务器 A 内存里没有太大问题

但是生产环境往往是：

```text
             ┌→ Server A
客户端   →  ─┼→ Server B
             └→ Server C
```

```text
-> 第一次登录请求进入 A
-> A 保存 Session
-> 第二次请求可能被负载均衡到 B
-> B 这里没有这个 Session
```

于是需要解决 Session 共享问题。一种常见方案：

```cpp
Server A ─┐
Server B ─┼→ Redis//一个纯内存的缓存应用
Server C ─┘
```

所有节点都从统一存储查询 Session

### Token 与 JWT

另一种思路是：尽量减少服务端保存登录会话状态，让客户端自己携带认证凭证

登录时，服务端下发 Token 给客户端。后续客户端每次请求自己带上 Token

例如 HTTP 请求头带上：

```http
Authorization: Bearer eyJhbGciOi...
```

JWT 是一种比较常见的 Token 格式。结构通常为：Header.Payload.Signature

Payload：

```json
{
  "userId": 10086,
  "exp": 1720000000
}
```

服务器收到以后验证签名。如果签名正确，就可以确认：

```text
Token 内容没有被随意篡改
并且由可信任的一方签发
```

但是 JWT 默认只是签名，不代表 Payload 被加密。

### JWT 与 Session 

JWT 的优势是：服务端收到 Token 后验证并读取身份，很多情况下不必查询集中式 Session。但是它也会带来新问题：

- Token 怎么主动失效？

- 用户退出怎么办？

- Token 被盗怎么办？

- 用户权限改变后旧 Token 怎么办？

- Token 过期如何刷新？

因此：JWT 和 Session 本质上是不同的状态管理策略，不存在谁是最优解

## HTTP 缓存

HTTP 缓存解决的是一个非常现实的问题：如果一个资源根本没有变化，为什么每次还要重新经过网络完整下载？

例如 logo.png，可能长时间不会改变。如果用户每次打开网页都发送请求从服务器下载 logo，会浪费带宽和服务器资源

所以 HTTP 设计了一整套缓存机制

### 强缓存

服务器可以返回：

```http
Cache-Control: max-age=3600
```

含义大致是：在未来 3600 秒内，可以直接认为这个响应仍然有效

浏览器再次请求时，优先检查缓存，如果没有过期就直接使用

### 协商缓存

缓存过期并不意味着服务器资源一定变了，如果资源本身没变，但因为过期而需要重新下载一个几十 MB 的文件非常浪费

于是浏览器可以询问服务器：“我手上的旧版本还能不能继续使用？”

这就是协商缓存

### Last-Modified

报文中记录资源有无改变

浏览器第一次请求资源，服务器第一次响应回复资源并带上以下请求头：

```http
Last-Modified: Mon, 10 Aug 2026 10:00:00 GMT
```

下次浏览器发送请求报文时带上以下请求头，询问服务端资源是否发生变化：

```http
If-Modified-Since: Mon, 10 Aug 2026 10:00:00 GMT
```

服务端返回：

```http
HTTP/1.1 304 Not Modified
```

浏览器得知资源未改变，于是继续使用原来的缓存

### ETag

另一种方式是资源版本标识，服务端第一次回复：

```http
ETag: "a81c923fe"
```

客户端下次请求带上：

```http
If-None-Match: "a81c923fe"
```

如果资源仍然是这个版本：

```http
304 Not Modified
```

浏览器继续使用缓存

### CDN 和 HTTP 缓存

CDN 是缓存资源服务器，这样用户想访问资源时可能不必请求源站，而是从 CDN 获取资源

降低源站服务器压力，让用户资源响应更快

比如，如果所有中国用户访问美国源站，那么每次都要跨越很远的网络，CDN 会把资源缓存在距离用户更近的节点，只有 CDN 本地没有目标资源时，才需要向源站索取资源

所以现代内容分发通常是：**DNS + HTTP 缓存 + CDN **共同完成的

## HTTPS 与 TLS

普通 HTTP 本身不提供加密能力，如果攻击者具备窃听通信链路的能力，就可能读取内容

为了保护数据安全，出现了 HTTPS，可以简单理解为加密版的 HTTPS

### HTTPS 本质是什么

HTTPS 可以先理解为：HTTP + TLS + TCP + IP

它不是完全重新发明一个 HTTP，而是在 HTTP 层和 TCP 层中间加一层 TLS 协议，用来作为 HTTP 报文的加密壳

### 对称加密

客户端和服务器使用共同密钥进行报文的加密、解密，比如客户端用 K 加密、服务器用 K 解密

对称密码非常**适合大量数据的高效加密**

但问题是，第一次通信时，这个共同密钥 K 从哪里来？

如果直接明文传输，一样会被攻击者截取——这就需要依赖非对称加密进行**密钥协商**

### 非对称密码与密钥交换

非对称密码体系通常涉及公钥、私钥

公钥可以公开，私钥只由所有者持有。一方用公钥加密，另一方用私钥解密。这就是非对称加密

现代 TLS 通常使用诸如 ECDHE 一类密钥交换机制，使双方能够在不安全网络上协商出共享会话密钥

之后真正的大量 HTTP 数据，仍使用高效的对称加密进行保护

为什么不持续用非对称加密保护对话数据？因为它手续繁杂，不利于高性能地传递数据

### 为什么还需要证书

即便可以协商密钥，还有一个问题：你怎么知道你正在协商密钥的对象真的是目标服务器？

假设攻击者能够冒充服务器，把自己的公钥交给客户端，客户端如果完全相信，就会产生**中间人攻击**

于是 TLS 需要**数字证书体系**

### CA 与证书链

服务器证书中一般包含：

```text
域名
公钥信息
有效期
签发者
数字签名
……
```

浏览器或操作系统预置信任一些根 CA

客户端收到网站证书后会验证：

```text
证书链是否可信
证书是否过期
访问域名是否匹配
签名是否正确
证书用途是否合法
```

验证通过之后，客户端才能确信：当前连接的服务器确实是目标网站

### 经典 TLS 握手整体流程

```text
客户端
 ↓
ClientHello
 ↓
声明支持的 TLS 版本、密码套件、密钥交换参数、随机数A 等

服务器
 ↓
ServerHello
 ↓
选择参数、返回证书、公钥、随机数B 等

客户端
 ↓
生成预主密钥，用公钥加密，发给服务端

服务端
 ↓
用私钥解密，获得预主密钥

双方
 ↓
通过与预主密钥、随机数等参数生成会话密钥
 ↓
握手完成，用会话密钥开始加密 HTTP 数据
```

## DNS

我们访问：www.example.com，但 IP 网络最终依赖 IP 地址进行寻址

因此需要一个系统完成：

```text
www.example.com
       ↓
203.0.113.10
```

这就是 DNS ：Domain Name System，域名系统

### DNS 层级结构

DNS 是分布式的，为什么？

理论上可以维护一个全球数据库，但是随着互联网规模扩大，会产生单点故障、访问瓶颈、延迟……于是 DNS 采用**分布式 + 层级化**

例如：

```text
www.example.com
```

可以从右往左理解：

```text
根 .
 ↓
顶级域 com
 ↓
权威域 example
 ↓
www
```

DNS 系统中存在：

```text
根 DNS
 ↓
顶级域 DNS
 ↓
权威 DNS
```

### 一次 DNS 查询大致发生什么

访问：

```text
www.example.com
```

首先一般会检查：浏览器缓存、操作系统 DNS 缓存、hosts 文件

如果没有结果，则通常询问本地 DNS，也就是离用户最近的 DNS，如果它也没有缓存，就会逐层查询：

```cpp
根 DNS //全世界只有13个根 DNS，它们保存顶级域名服务器的地址，比如 .com DNS 地址、.cn DNS 地址……
 ↓
.com 顶级域名 DNS//顶级域名：.com 和 .cn 等等，它们保存二级域名 DNS 服务器的地址
 ↓
example.com 权威 DNS//二级域名
 ↓
得到 IP
```

然后把结果返回给客户端，并进行缓存

### DNS 为什么通常使用 UDP

传统 DNS 查询通常**请求小、响应小、一问一答**

UDP 不需要建立 TCP 连接：

```text
DNS Query
 ↓
DNS Response
```

所以经典 DNS 查询通常使用：

```cpp
UDP 53 // UDP协议、53号端口
```

但有些情况也会使用 TCP

## WebSocket

WebSocket 是一种长连接、全双工的协议，此处只做简单介绍

什么是全双工？就是双方都可以主动发送数据。所以适合：实时消息、长连接、服务器主动推送

常用的聊天软件和有些游戏就是依靠 WebSocket 

传统 HTTP 通常采用：

```text
客户端请求
 ↓
服务器响应
```

如果服务器需要主动向客户端推送消息，就比较麻烦

一种最简单的方案是不断轮询：

```text
客户端：
有消息吗？

服务器：
没有。

客户端：
有消息吗？

服务器：
有，然后回复
```

这种方式会产生大量无意义请求，占用带宽和资源

于是出现类似 WebSocket 之类的长连接协议

### WebSocket 建立

WebSocket 最开始通常通过 HTTP 请求进行协议升级

客户端通过 HTTP 协议申请建立 WebSocket ：

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

服务器同意后也升级为 WebSocket ：

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

之后双方交流不再使用HTTP 请求响应协议，而是切换到 WebSocket 帧协议。而底层 TCP 连接通常仍然是原来的连接

### WebSocket 自己定义消息边界

它仍然是基于字节流 TCP，所以需要自己划分消息边界

它自己定义帧格式，包括：

```text
FIN
Opcode
Mask
Payload Length
Payload
```

因为 WebSocket 需要解决：

```text
消息多长？
文本还是二进制？
是否分片？
是不是 Ping？
是不是 Pong？
是不是 Close？
```

## RPC 与微服务通信

RPC ：Remote Procedure Call，远程过程调用。什么意思？

举个例子，订单服务希望调用用户服务，但两个服务属于不同进程甚至不同机器：

```java
userService.getUser(10086);
```

如果完全自己实现网络通信，需要建立连接、序列化、设计报文、解析数据、处理异常……非常复杂

所以产生 RPC 机制，它封装好了通信底层，希望让程序员调用远程服务时如同在调用本地函数

### RPC 背后实际发生什么

表面：

```java
User user = userService.getUser(10086);
```

背后：

```text
参数
 ↓
序列化
 ↓
RPC 请求报文
 ↓
网络传输
 ↓
服务端反序列化
 ↓
调用真实方法
 ↓
结果序列化
 ↓
返回响应
```

### RPC 报文

RPC 报文通常会包含：

```text
协议版本
请求 ID
服务名
方法名
序列化类型
消息长度
参数内容
Trace 信息
```

例如：

```text
┌───────────────┐
│ Magic Number  │
├───────────────┤
│ Version       │
├───────────────┤
│ Request ID    │
├───────────────┤
│ Method        │
├───────────────┤
│ Body Length   │
├───────────────┤
│ Body          │
└───────────────┘
```

### 序列化

程序中的对象，人肉眼可见：

```java
User {
    id = 10086,
    name = "Tom"
}
```

不能直接把内存对象通过网络扔给另一台机器。需要转换成双方都能理解的字节，这就是序列化：

```text
对象
 ↓
序列化
 ↓
字节
 ↓
网络
 ↓
字节
 ↓
反序列化
 ↓
对象
```

常见的序列化方式有：

JSON：

```text
字符串
可读性好
调试方便
体积相对较大
解析开销相对较高
```

Protobuf：

```text
二进制
体积较小
解析效率高
需要 Schema
```

### 服务发现

假设订单服务要调用：

```text
user-service
```

生产环境可能存在：

```text
10.0.0.11:8080
10.0.0.12:8080
10.0.0.13:8080
```

而且实例会动态：

```text
上线
下线
扩容
缩容
```

所以需要服务发现——调用方获得健康实例列表以后，再进行负载均衡选择一台机器

### RPC 超时

如果：

```text
A → B → C → 数据库
```

数据库一直卡住：

```text
C 等
B 等
A 等
```

最终可能造成：

```text
线程堆积
连接堆积
内存增长
服务雪崩
```

所以远程调用必须有明确超时

### gRPC

gRPC 是很典型的现代 RPC 框架。

常见技术结构：

```cpp
RPC
 ↓
Protobuf//和 JSON 一样都是把数据转换成一种序列化格式，但 JSON 转换成字符串，Protobuf 转换成二进制，更加高效
 ↓
HTTP/2//gRPC 通常基于 HTTP2
 ↓
TCP
```

因此后面理解 HTTP/2 的 Stream 和多路复用以后，再来看 gRPC 会容易很多

## HTTP/2

HTTP/1.1 面临的一个重要问题是：**一个连接内高效并发多个请求的能力有限**

一个页面可能同时需要：

```text
HTML
CSS
JavaScript
图片
字体
API
```

为了提高并发能力，HTTP/1.1 时代浏览器经常为同一站点建立多条 TCP 连接，但这样开销较大

所以HTTP/2 希望做到**在一条 TCP 连接中同时处理大量 HTTP 请求**

### 二进制分帧

HTTP/1.1 网络报文类似：

```text
GET / HTTP/1.1
Host: ...
```

HTTP/2 不再直接使用这种纯文本报文形式。

而是：二进制帧。它是 **HTTP/2 对应用层消息进行传输时定义的一种基本传输单元**

一个请求头可以被包进一个二进制帧；一个请求体可以被拆分为多个部分，分别包进多个二进制帧……

例如：

```text
HEADERS
DATA
SETTINGS
WINDOW_UPDATE
RST_STREAM
PING
```

### Stream

HTTP/2 最重要的概念之一：Stream

一个 HTTP/2 Stream **代表一次独立的 HTTP 请求/响应交互**，它由许多二进制帧组成

一条 TCP 连接中，可以同时存在很多 Stream，也就是多个 HTTP 报文被拆成多部分交叉传输：

```text
TCP Connection

├── Stream 1：HTML
├── Stream 3：CSS
├── Stream 5：JS
├── Stream 7：API
└── Stream 9：图片
```

不同 Stream 的帧可以交错：

```text
S1 HEADERS
S3 HEADERS
S1 DATA
S5 HEADERS
S3 DATA
S1 DATA
```

接收方通过 Stream ID 重新把数据归属到不同请求中

这就是：多路复用

### Header 压缩

HTTP 请求头经常重复，每个请求都要带这些字段：

```http
User-Agent: ...
Cookie: ...
Accept: ...
```

HTTP/2 使用 HPACK 对 Header 做压缩，也就是**让客户端和服务器共同维护一张“Header 字典”**

起初双方已经拥有预定义好的字典，表项**由索引和请求头字段组成**

```
索引       Header
1         :authority
2         :method: GET
3         :method: POST
4         :path: /
...
```

于是发送方发送时不再需要在请求头中写 `"method：GET"`，而是发送对应索引，接收方按照索引查字典，就能知道字段值

如果是第一次发送该字段，会发送索引+字段内容，双方都会在字典中动态记录，下次就只用发索引了

本质就是**用一个更短的索引代替完整 Header**，减少重复数据发送

### HTTP/2 存在 TCP 队头阻塞

虽然 HTTP/2 解决了 HTTP 层面的请求排队问题，但底层仍然是 TCP

TCP 要求：字节按顺序交付。如果发现前面的某个报文丢失，发送方就会停止发送后续报文，而是不断重发丢失的报文

而 HTTP/2 所有 Stream 又共享同一条 TCP，所以一个 TCP 层丢包，有可能影响这条连接中的多个 HTTP/2 Stream

这就是 **TCP 层队头阻塞**，是 TCP 的局限性

------

## HTTP/3

HTTP/3 做了一个非常大的变化，为了解决 TCP 队头阻塞，它在传输层采用了 UDP 而不是 TCP

并且在 HTTP 和 UDP 之间实现了另一个协议 QUIC，用来约束消息可靠性、有序性等等

```text
HTTP/3
 ↓
QUIC
 ↓
UDP
```

### 为什么不用 TCP 

 TCP 的一些设计已经难以满足 HTTP 进一步演进：

```text
严格按序字节流
连接建立成本高
协议很多逻辑位于内核，不易更改
连接对网络地址变化较敏感
```

于是 QUIC 选择：**在 UDP 上重新实现现代传输能力**

QUIC 自己实现：

```text
可靠传输
重传
流量控制
拥塞控制
多路复用
TLS
连接管理
```

所以 UDP 在这里更多提供数据报、端口、操作系统中成熟的 UDP 传输入口等底座功能，其他所有约束都靠 QUIC

### QUIC 如何改善队头阻塞

假设：

```text
Stream A
Stream B
Stream C
```

Stream A 某段数据丢了

QUIC 可以让 Stream B、Stream C 继续独立交付。因为 QUIC 自己从传输层就知道哪些数据属于哪个 Stream

而 如果是 HTTP/2：TCP 并不知道哪些字节属于哪个 HTTP Stream，所以底层一个缺失字节可能影响整条 TCP 字节流

### QUIC 连接迁移

传统 TCP 连接通常与 源 IP、源端口、目标 IP、目标端口 紧密相关

举个例子，手机从 WIFI 切换到 5G，源 IP 可能发生变化，原 TCP 连接通常会受到影响甚至断开

QUIC 使用 Connection ID 而不是 源 IP、源端口、目标 IP、目标端口 来唯一标识一条连接

这样在满足条件时，即使网络地址改变，也可能继续维持原来的逻辑连接，这对移动设备非常重要

------

## 在浏览器访问网址时的应用层流程

当用户在浏览器输入：

```text
https://www.example.com/users
```

背后实际上可能经历：

```text
1. DNS

www.example.com
 ↓
获得服务器 IP


2. 建立网络连接

HTTP/1.1 / HTTP/2：TCP + TLS

或是

HTTP/3：QUIC + TLS


3. 浏览器构造 HTTP 请求

GET /users HTTP/...


4. 服务端认证

Cookie + Session 或者 Token


5. HTTP 缓存判断

Cache-Control / ETag / Last-Modified


6. 服务端业务处理

HTTP Server
 ↓
RPC
 ↓
其他微服务
 ↓
数据库 / Redis


7. HTTP 响应返回 HTML、CSS 以及其他数据……


8. 浏览器解析数据并最终展示页面
```

如果是实时业务：

```text
WebSocket
 ↓
长期双向连接
 ↓
服务器主动推送
```

所以这些应用层知识实际上围绕同一个核心问题不断演进：

> **如何让不同主机上的应用程序，在真实、复杂、存在延迟和故障的网络环境中，高效、安全、可靠地完成业务通信。**

HTTP 解决：

```text
应用之间如何表达请求和响应
```

Cookie、Session、Token 解决：

```text
HTTP 无状态情况下如何识别用户和保存会话状态
```

HTTP 缓存解决：

```text
如何避免重复传输没有变化的数据
```

TLS 解决：

```text
如何在不可信网络中安全通信
```

DNS 解决：

```text
如何通过域名找到目标网络服务
```

WebSocket 解决：

```text
如何建立长期双向实时通信
```

RPC 解决：

```text
如何让分布式服务之间更方便地进行远程调用
```

HTTP/2 解决：

```text
如何提高 HTTP 在 TCP 上的并发效率
```

HTTP/3 与 QUIC 则进一步解决：

```text
如何突破传统 TCP 架构的一部分性能和连接限制
```

这就是应用层的工作机制
